# AI QA platform — prototype

Describe a test in plain language, review the code, run it. Get a real Playwright
test you own.

```
npm run dev     # → http://127.0.0.1:5173
```

Or from the terminal:

```
npm run gen -- "log in as the standard user and check the products page appears"
npm test
```

The output is an ordinary `.spec.ts` file in `tests/generated/`. Nothing in this
repo is needed to run it — that portability is the product's main argument, see
[docs/competitor-analysis.md](docs/competitor-analysis.md).

## Status

Verified 1 Oct 2026 against `https://www.saucedemo.com`: **4 specs generated by
Claude, 4 passing**, including a screenshot-comparison baseline. Web UI working end to end —
describe → review → approve → run, with pass/fail and the real Playwright error
shown inline.

## The UI

Four steps, one page:

1. **Describe** — plain language, or one click from the cached examples
2. **Review** — the generated code, with where it came from and what it cost
3. **Approve** — *nothing is written to disk until a human says yes*
4. **Run** — pass/fail per test, with the actual Playwright failure when it fails

The review step is the point, not decoration. A generated test that asserts the
wrong thing still passes, and then it hides the bug instead of catching it. The
`/api/generate` and `/api/approve` endpoints are deliberately separate so the
suite can only ever be changed by a human decision.

The server is local-only (`127.0.0.1`) because it spawns processes. The filename
sent to `/api/run` is checked against the files that actually exist before
anything is spawned, the binary is invoked with an argument array rather than a
shell, and `/api/approve` rejects a path that isn't a plain `*.spec.ts` basename
or whose body doesn't import `@playwright/test`.

```bash
npm install
npx playwright install chromium
```

Optional, for real generation:

```bash
cp .env.example .env              # add ANTHROPIC_API_KEY
```

A key comes from [console.anthropic.com](https://console.anthropic.com) and is
**separate from a Claude subscription**. One generated test costs a few cents
(`claude-opus-5`, ~$5/M input, ~$25/M output); the CLI prints the exact cost.

## How it works

```
"log in as a locked out user"
        │
        ▼
   cache lookup ──── hit ──→ replay, no API call
        │
       miss
        │
        ▼
  Claude (claude-opus-5)      system prompt pins:
  src/prompt.ts                 • output format
        │                       • role/label locators over CSS
        ▼                       • web-first assertions, no waitForTimeout
   parse + validate             • screenshots only when asked
   src/claude.ts
        │
        ▼
  tests/generated/*.spec.ts  ──→  npx playwright test
```

| File | Role |
|---|---|
| `src/prompt.ts` | The system prompt. This is the actual product. |
| `src/claude.ts` | API call, response parsing, validation, cost reporting |
| `src/cache.ts` | Request-keyed cache — free repeats, offline demo |
| `src/target.ts` | What the generator may know: credentials, notes, pages |
| `src/inspect.ts` | Captures each page's accessibility tree from the live site |
| `src/generate.ts` | Cache-first orchestration, writes the spec file |
| `src/cli.ts` | `npm run gen` |
| `src/server.ts` | Local HTTP API + static host (no framework, no extra deps) |
| `src/runner.ts` | Spawns Playwright, parses the JSON report into results |
| `public/` | The UI — one HTML page, one CSS file, one JS file |

**Cache-first is deliberate.** A demo must not depend on a network call succeeding
in the room, and regenerating an unchanged request should cost nothing.

## Why the generator sees the page

The hardest lesson from building this, and the part worth presenting:

A description alone is not enough. Asked to "add a backpack to the cart", the model
produced `getByRole("button", { name: "Add to cart Sauce Labs Backpack" })` — fluent,
plausible, and wrong: the real accessible name is just "Add to cart". It had never
seen the page. No wording of the prompt fixes that.

So `npm run inspect` captures the accessibility tree of each page with Playwright's
`ariaSnapshot()` — logging in first where a page needs it — and that tree goes into
the prompt. Re-run after a UI change. Same request, with the tree supplied:

```ts
// TODO: all six "Add to cart" buttons share the same accessible name, so the
// backpack's button is identified by its unique id.
await page.locator("#add-to-cart-sauce-labs-backpack").click();
```

It found the ambiguity, chose the id, and said why. This is the same conclusion
Playwright reached with its Generator agent, which verifies selectors against a
live browser as it writes.

Every spec in `cache/` and `tests/generated/` is real model output, generated and
verified on 1 Oct 2026 — nothing in this repo is hand-written and presented as
generated.

The limit of this approach is in `examples/known-limitation-burger-menu.spec.ts`,
kept as a failing test on purpose: snapshots capture pages in their initial state,
so anything that only appears after a click isn't in the tree. The model noticed
and said so in a TODO rather than failing silently — which is exactly why the
review step exists.

## Pointing it at another site

Verified on a real production site, not just a practice one — see
`examples/wikipedia-search.spec.ts`, generated against Wikipedia and passing.

1. Write the new site's config in **`target.local.json`** (gitignored, overrides
   `target.json`): its description, any test accounts, and the pages to capture.
2. Capture: `BASE_URL=https://your-site.com npm run inspect`
3. Generate and run with the same `BASE_URL` set.

```jsonc
{
  "description": "What the site is, in a sentence or two.",
  "credentials": [{ "role": "admin", "username": "...", "password": "..." }],
  "notes": ["Anything non-obvious about how it behaves."],
  "inspect": {
    "signIn": {
      "credential": "admin",
      "username": { "label": "Email" },      // or placeholder / role+name / css
      "password": { "label": "Password" },
      "submit":   { "role": "button", "name": "Sign in" },
      "dismiss":  { "text": "Accept cookies" },   // optional cookie banner
      "confirm":  { "text": "Dashboard" }         // proves sign-in worked
    },
    "pages": [
      { "name": "login", "path": "/login" },
      { "name": "dashboard", "path": "/app", "requiresSignIn": true }
    ]
  }
}
```

If a page renders late (React/Next/Vue), the capture already waits for the tree to
stop changing and warns if it came back near-empty. For a slow app add
`"waitFor": { "text": "Dashboard" }` to that page, or raise `inspect.settleMs`.
For content inside an iframe, set `"frames": true` on the page.

**Capture every page the flow touches.** If a test navigates somewhere that isn't
in `pages`, the model is guessing again — that's what the Wikipedia example shows.

**A ready config for Feedboon** is in `examples/target.feedboon.json` — copy it to
`target.local.json`, fill in the two TODOs (your local account, and a project slug),
and run with `BASE_URL=http://localhost:3000`. It was written from the Feedboon repo,
so the login locators and routes are its real ones, not guesses.

Only test a site you are allowed to test: your own, your employer's or client's
with their agreement, a staging environment, or a public practice site. Automated
sign-in attempts against someone else's production system are not yours to run.
